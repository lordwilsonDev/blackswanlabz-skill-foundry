# Operations

## Local service

Run from the project root, bind to 127.0.0.1:8787, and use the private state/config generated by the CLI. A launchd template is supplied in `deploy/`; replace every placeholder and verify permissions before installing it. It was not installed as a persistent login service during this build.

`/healthz` is liveness only and always reports `production_ready:false`. Authenticated `/api/integrity` reconciles evidence and content hashes. Authenticated `/metrics` exposes source, skill and recent-run gauges (the run gauge covers the most recent 50 runs, not lifetime totals). JSON request logs contain latency and route. Monitoring alert example requires an operator-provisioned Prometheus scrape target and credential; no external alerts were sent.

## Credentials and permissions

State directory: 0700; config/credential files: 0600. Keep the builder token with the operator and give the reviewer token only to an independent reviewer. Rotate by replacing a principal's token hash and restarting. Remove a principal to revoke access. Keep runtime and backup files outside shared/public folders. No credential is embedded in code or exported skill packages.

## Backup / restore / rollback

For a consistent operational backup, stop the service, run `python -m foundry --root runtime backup NEW_DIRECTORY`, and restart. This uses SQLite backup APIs instead of copying live WAL files. To restore, stop service, preserve current state, point `--root` at the backup, run `integrity` and the deployment checker, then start. The durable outbox repairs an interrupted spine write without duplicate evidence. A local restore exercise is recorded in reports; off-host recovery is not proven.

Skill versions are immutable packages. To roll back behavior, select a previously reviewed version by ID; source validity is checked again at every run. Source revocation makes all dependent versions stale, so rollback cannot bypass invalidation. To roll back application code, stop service and use a reviewed Git revision; database format is v1, and no destructive migrations are implemented.

## Linux worker deployment

Build the supplied worker image and obtain its image ID:

```sh
docker build -f deploy/Dockerfile.worker -t foundry-worker .
export FOUNDRY_WORKER_IMAGE="$(docker inspect --format='{{.Id}}' foundry-worker)"
python scripts/foundry_check.py --root runtime
```

Before production, pin the base image by digest, scan it, run Linux failure tests and load tests, and approve container-host permissions. The local checker exits 0 only when integrity and actual sandbox execution pass. `--production` deliberately exits 2 until missing acceptance evidence is implemented and independently reviewed; do not change it to success just to make deployment green.

## Incident response

Stop the process to stop new requests. If a source is wrong, revoke its ID using the reviewer role, inspect affected STALE packages, retain receipts, then import a corrected new revision. On integrity failure, preserve the entire state directory and logs; do not reseed or overwrite evidence. Restore from a verified backup and compare an external trusted anchor if one exists. No external anchor was provisioned in this build.

## Capacity and service limits

Sources: 200,000 characters each; assembly: up to 12 sources, up to 24 structured lines per source; HTTP body: 600 KB; worker: 8-second deadline and 2-second CPU limit; model: 45-second request timeout, 2048 requested output tokens and 200 KB response cap. Keyword retrieval currently scans the active corpus in memory. SQLite serializes mutations. This is not designed for unbounded ingestion or internet-facing concurrent traffic. A production deployment needs measured target-scale capacity and admission control.
